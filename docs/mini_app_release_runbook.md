# Выпуск Mini App на существующем VPS

Дата: 11.10.2026. Первоначально подготовлено в dev; закрытый рабочий выпуск b15d275 выполнен после явного согласования владельца. Фактический результат и оставшиеся проверки: [протокол выпуска](mini_app_release_status.md). Общая кнопка/Main App и открытие всем пользователям пока не выполнены. Ниже сохранён порядок выпуска и восстановления.

## Фактическое устройство и проверка перед выпуском

Docker установлен на VPS, а не «на поддомене». Сейчас Compose запускает отдельные bot и worker. Поддомен обслуживает хостовый nginx. Подготовленный релиз добавляет api; все три процесса используют один образ, одну базу и общие правила. Только bot получает Telegram updates; только worker отправляет очередь уведомлений и выполняет фоновые задачи. API не запускает polling/планировщик/отправитель.

11.10.2026 выполнен read-only SSH-аудит: оба контейнера работают, Compose 5.6.0; свободно 2346 МБ диска и 503 МБ доступной RAM; время VPS синхронизировано NTP. SQLite v8: integrity_check=ok, foreign_key_check без ошибок. nginx -t успешен, таймер auto-deploy активен. Эти показатели не заменяют измерение нагрузки API и расхода памяти сборки.

Адрес после выпуска: https://meetcalendar.fin-partner.pro/app/. Nginx проксирует /app/ и /api/v1/ на 127.0.0.1:8770; /health/ready наружу не публикуется. Корень сайта и /privacy/ остаются статическими. Ссылку с fin-partner.pro не добавлять: владелец намеренно оставляет поддомен самостоятельным.

Уточнение исходного предложения: собранный frontend отдаёт API-контейнер через nginx. Frontend включён в тот же образ, поэтому при обновлении и откате он меняется одновременно с API; отдельное копирование dist в /var/www не требуется. CSP, no-store, no-referrer и запрет выдачи файлов вне dist применяет FrontendFiles. API-порт доступен только с VPS.

## Подготовленные файлы

- Dockerfile: сборка React/TypeScript/Vite через pnpm lockfile; Python с API-зависимостями; непривилегированный UID 10001.
- compose.yaml: bot, worker, api; API memory limit 256 МБ, CPU 0.5, один Uvicorn worker, concurrency 32; readonly filesystem и существующие защищённые mounts.
- api/production.py: явный рабочий режим, настоящий общий Google-клиент, проверка схемы без автоматической миграции, отдельный API-журнал.
- release_database.py: резервная копия SQLite API, предварительный переход v8→v11 на копии, целостность и восстановление. Существующая резервная копия не перезаписывается. Подтверждение maintenance означает, что исполнитель уже проверил остановку всех писателей; параметр сам не останавливает контейнеры.
- auto_deploy.py: контекст включает frontend, предварительная проверка API, согласованное пересоздание и откат трёх сервисов. Docker/Compose/миграции по-прежнему требуют управляемого выпуска.
- CI: dev и main; Python/API, frontend и сборка Docker. Новый dev push не запускает серверный deploy, который следит только за main.

## Порядок управляемого выпуска

Исполнитель выполняет после отдельного согласования, из /opt/meeting-bot. Перед переносом кода зафиксировать точные старый и новый SHA и image ID, сохранить старые инфраструктурные файлы/nginx/auto_deploy.py вне checkout. Убедиться, что новые CI-проверки успешны для выбранного SHA. Не запускать старый deploy_vps.py с заменой .env; доставка кода только из проверенного Git-дерева без data, logs, .env, .secrets.

1. Приостановить таймер и дождаться завершения его службы (не прерывать выполняющийся deploy). При следующем запуске установить baseline на согласованный SHA только после успешной ручной установки. Не использовать --initialize для существующего baseline и не обходить manual_change_reason.

   systemctl stop meeting-bot-auto-deploy.timer
   systemctl is-active meeting-bot-auto-deploy.service

2. Сохранить прежний образ отдельным неизменяемым release-тегом, не только meeting-bot:rollback. Скопировать код согласованного SHA отдельно от секретов. Собрать новый образ до остановки бота; контролировать доступную RAM/диск. При нехватке ресурсов остановиться, не перезагружать VPS и не очищать чужие образы/данные. Сохранить возможность запустить прежний Compose и образ.

3. Убедиться, что API ещё не опубликован. Остановить bot/worker, а при повторной попытке и api; docker compose ps -a должен подтвердить остановку. Другие проекты и nginx не останавливать. Краткая недоступность чат-бота входит в согласуемое окно обслуживания.

4. Создать закрытый каталог резервных копий с владельцем UID 10001 и mode 700. Запустить миграцию ровно одним процессом из нового образа. BACKUP заменить уникальным путём, например data/backups/pre-miniapp-YYYYMMDD-HHMMSS.sqlite. Через compose run не запускать зависимые сервисы; команда переопределяет обычный launcher:

   docker compose run --rm --no-deps api python -m meeting_bot.release_database migrate --database data/bot.sqlite --backup BACKUP --maintenance-confirmed

   Инструмент требует исходную схему v8, сохраняет резервную копию v8 с mode 600, создаёт BACKUP.rehearsal и проверяет полный переход к v11 на ней. Затем мигрирует рабочую SQLite. При любой ошибке службы остаются остановленными; возможна частичная последовательность ревизий v9/v10, поэтому нельзя просто включать старый код. Проверить и восстановить backup при необходимости. Не копировать отдельный файл SQLite поверх активного WAL.

5. Обновить только новые настройки серверного .env, сохранив остальные строки и актуальный Google refresh token. Не копировать локальный .env. Первоначальные значения: MINI_APP_MODE=production; MINI_APP_ORIGIN=https://meetcalendar.fin-partner.pro; MINI_APP_ENABLED=true; MINI_APP_RESTRICTED=true. Подтверждённый второй Telegram ID должен уже быть указан как BOT_SERVER_TEST_VISITOR_ID. BOT_SERVER_TEST_MODE не менять: ограничение Mini App независимо от доступности чат-бота. Настройки согласия берутся из существующих POLICY_URL/POLICY_VERSION, календарь из BOT_CALENDAR_ID.

6. Выполнить проверку нового API без сети и без побочных действий, затем запустить три сервиса:

   docker run --rm --network=none --read-only --user 10001:10001 --mount type=bind,source=/opt/meeting-bot/.env,target=/app/.env --mount type=bind,source=/opt/meeting-bot/data,target=/app/data --mount type=bind,source=/opt/meeting-bot/logs,target=/app/logs meeting-bot:local python scripts/run_server.py api --check
   docker compose up -d --no-build bot worker api

   Проверить состояния контейнеров, отсутствие restart loop, API healthy и ответ http://127.0.0.1:8770/health/ready. Readiness проверяет доступность/версию базы, но не Google/Telegram. Провести read-only контроль прав .env/data/logs и версии v11.

7. Установить только конфиг nginx данного поддомена после сравнения с фактическим конфигом. Сначала nginx -t; только при успехе reload nginx. Проверить корень, /privacy/, /app/, выдачу JS/CSS, запрет /.env и внешнего /health/ready. Не изменять другие сайты, сертификаты или firewall; порт 8770 наружу не открывать.

8. Проверить с двух уже разрешённых Telegram-аккаунтов: вход, роли, текущие реальные шаблоны/интервалы и статус Google. По отдельному согласованию провести одну настоящую контрольную заявку с тестовым email, уведомление владельцу через бота, согласование, ровно одно событие/приглашение Google и отмену с удалением события. Посетитель не подключает свой Google-аккаунт. Зафиксировать результаты без контактов. После внешних эффектов не делать слепой откат базы: сначала сопоставить Google и очередь уведомлений.

9. Сверить рабочее расписание с принятыми пожеланиями владельца: пн/вт/чт/пт, начала 10:30/11:30/13:30/15:00/16:30, окончание до 18:00. Миграция не меняет опубликованные интервалы, существующие встречи и значения настроек. Изменение рабочего расписания выполнять штатным админ-сценарием с просмотром затронутых записей, а не копированием тестовых fixtures.

10. Измерить реальные ресурсы и нагрузку; согласованные численные пределы MA-5 подтвердить на VPS. После успешной проверки открыть MINI_APP_RESTRICTED=false (если бот сам ограничен, API сохраняет его ограничение), пересоздать api и повторить первый вход новым пользователем. Ручной допуск к записи сохраняется. Включить Main App и общую кнопку меню на постоянный /app/. У владельца и второго аккаунта явно сбросить персональные временные меню в MenuButtonDefault, иначе они перекроют общую кнопку старым туннелем. Сохранить прежние меню для восстановления и проверить оба чата и общий вход.

11. Установить согласованный новый auto_deploy.py за пределами checkout, проверить его --check и сохранить baseline выбранного SHA атомарно. Убедиться, что все три контейнера используют один image ID и исходные инфраструктурные файлы совпадают с одобренным Git-деревом. Возобновить таймер. Старые image/code/nginx/DB backups сохраняются до завершения наблюдения; автоматическая очистка не выполняется.

Временный MINI_APP_ENABLED=false отключает API, сохраняя чат и worker. API healthcheck при этом будет неуспешным; автодеплой нужно приостановить на время такого обслуживания, иначе он сочтёт API нездоровым. Политика сессий не меняется: initData 5 минут, сессия 30 минут, bearer только в памяти, идемпотентность 24 часа. Preview-коррекция часов не переносится в production: проверено NTP VPS.

## Восстановление

До открытия пользователям и до внешних эффектов: остановить bot/worker/api, восстановить v8 из подготовленного backup через новый образ, вернуть прежние Compose/образ/nginx и прежний auto_deploy.py/baseline. Проверить v8/integrity и запустить только старые bot/worker. Восстановление базы:

   docker compose run --rm --no-deps api python -m meeting_bot.release_database restore --database data/bot.sqlite --backup BACKUP --maintenance-confirmed

Серверный .env не заменять старой копией целиком: Google мог обновить refresh token. Возвращать только настройки Mini App/меню. После приёма настоящих новых заявок или изменения Google простой возврат v8 потеряет новые записи: сначала закрыть вход Mini App, остановить писателей, сохранить текущее состояние и подготовить согласованное восстановление с учётом внешних эффектов.
