## 1. Как вести план

1. ТЗ определяет конечное поведение; этот файл — порядок, статусы, чекбоксы и доказательства. Одно решение не переписывается разными словами в нескольких местах: здесь ссылка на ID требования/решения.
2. Перед работой назвать этап, его статус и разрешённый результат. MA-0/MA-0V не дают права создавать API, менять бот или инфраструктуру. После поручения на код работать автономно в указанном объёме; подтверждение каждого обычного действия не требуется.
3. Статусы: «Не начат», «В работе», «Ожидает решения пользователя», «Завершён». «Завершён» — только по проверенным критериям; выполненный код и принятый пользователем внешний вид отмечаются разными пунктами.
4. После существенного изменения обновлять чекбокс и журнал: дата, что изменено, причина, какие файлы, проверка и её результат, что осталось. Журнал работ не заменяет безопасные технические логи программы.
5. При новом требовании определить ID, затронутый этап, проверку, влияние на уже выполненное. Обязательный дефект завершённого этапа открывает его повторно либо связанный корректирующий пункт; статус «Завершён» не прячет новую работу.
6. Не спрашивать повторно уже выбранные правила/технологии; спорное или новое решение явно помечать. Предложение агента не считается ответом пользователя. Дизайн, API, черновики и права имеют конкретные точки решения в разделе 3.
7. Исполнитель сам подготавливает среду и проверяет ссылки/тесты. Владелец проверяет смысл и внешний вид кнопками. Непроверенный WebView, Google или сервер обозначаются как непроверенные, а не как успешные по косвенным признакам.
8. Commit/push — по поручению пользователя; при смене чата сохранять рабочую копию/статус и указать незакоммиченные файлы. Main автоматически связан с рабочим сервером; переход к нему не является обычным сохранением прогресса.

### Шаблон записи после этапа

- Дата и этап; выполненные требования/решения.
- Изменённые файлы и существенные причины.
- Автоматические проверки: что запускалось, результат; либо почему проверка неприменима.
- Визуальная/ручная проверка: контур, роль, размер экрана, действия, ожидаемый/фактический результат.
- Открытые дефекты: серьёзность, владелец действия, связанное требование/этап.
- Новый статус и следующий разрешённый шаг; без секретов и контактных данных.

## 2. Последовательность и зависимости

MA-0 → MA-0V → MA-1 → MA-2 → MA-3 → MA-4 → MA-5 → MA-6.

Проверки выполняются внутри каждого этапа. MA-5 объединяет и повторяет только нужную регрессию, а не откладывает все испытания до конца. Ранний тест Telegram-auth в MA-2 выявляет проблемы WebView/HTTPS до полного интерфейса. Показ посетителя и администратора по частям не сокращает согласованный полный scope первого релиза.

Предварительные макеты в MA-0V можно обсуждать до выбора UI-библиотеки; сборка рабочего preview позже требует разрешения программного этапа. Новый этап MA-0V добавлен между существующими ID без переименования MA-1–MA-6, чтобы ссылки на требования оставались стабильными.
