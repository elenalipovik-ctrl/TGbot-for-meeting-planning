## 1. Назначение, источники и границы

Mini App дополняет работающий чат-бот календарным интерфейсом, формами и списками. Посетитель получает доступ, выбирает время, подаёт и отменяет свои заявки. Администратор управляет допуском, расписанием, шаблонами, решениями и предупреждениями. Оба интерфейса работают с одними посетителями, заявками, удержаниями, Google Календарём и очередью уведомлений.

Указание создать ТЗ Mini App не закрывает эти пункты и не разрешает перезагрузку сервера. Этот документ не является юридическим заключением и не переутверждает политику обработки данных.

### 1.2. Что входит в первую версию Mini App

- Русский интерфейс посетителя и одного администратора внутри Telegram.
- Telegram-аутентификация, проверка допуска и прав на каждый объект.
- Календарь опубликованных слотов, формы заявки и контактов, история собственных заявок.
- Все основные административные действия из матрицы раздела 4.
- HTTPS API на принятом FastAPI поверх общего Python-слоя приложения.
- Общие правила, SQLite, Google Calendar, фоновые задания и Telegram-уведомления.
- Безопасная работа двух интерфейсов одновременно, повторов и восстановления после сбоев.
- Проверки, согласованные миграции, инструкция запуска и отключения Mini App.

Не входят: перенос без отмены, автоматическое создание видеоссылок, новые администраторы/календари, платежи, CRM, отдельная почтовая служба, личный Google OAuth посетителя, самостоятельная система бронирования, замена SQLite, Redis, публичный кабинет с паролем. Пункт «v2» исходного ТЗ перечисляет возможное развитие и не означает автоматического включения всех этих возможностей.

Сайт public_site/ остаётся информационной страницей и политикой. Он не является существующим Mini App. В рамках подготовки документации не изменяются сайт, код, базовые документы бота и CI.

**Выявленные границы, которые нужно учесть при реализации:**

1. Нельзя просто открыть методы service.py наружу. Например, confirm_with_google и begin_calendar_creation не принимают Telegram actor: сейчас админ-проверка выполняется в AdminFlow. API обязан вызывать общий защищённый сценарий с серверным actor; проверки только в кнопках недостаточно.
2. Проверка домена видеоссылки находится в admin_flow.py, телефон и лимиты текста — в visitor_flow.py. Их следует сделать общими для чата и API, сохранив действующие правила. API не должен иметь более слабую валидацию.
3. visitor_dialogs и admin_dialogs хранят шаги чата; drafts связывается с bookings, но контактные поля чат фактически сохраняет и в visitor_dialogs. Автоматическая общая синхронизация форм ещё не реализована. Нужен явный проект состояния черновика, а не предположение, что оба интерфейса уже совместимы на каждом шаге.
4. Списки и статистика частично строятся SQL-запросами в flow-классах; веб-слою нужны общие запросы с проверкой владельца и пагинацией. Не возвращать целые строки SQLite клиенту.
5. Закрытие целого дня уже есть в BookingService.close_day, хотя отдельной кнопки этого действия в просмотренном AdminFlow нет. Mini App должен использовать этот метод. Полные списки допущенных/заблокированных — требование исходного ТЗ, которое необходимо реализовать общими выборками, а не копировать ограниченный список 10 запросов чата.
6. Разрешения заблокированного пользователя требуют решения D-05: текущий VisitorFlow запрещает ему и «Мои заявки»/«Мои данные». Блокировка сама по себе не отменяет встречи. Проект не должен молча дать Mini App дополнительные права.
7. initialize_database отклоняет схему новее SCHEMA_VERSION. После повышения версии схемы старый образ может не запуститься, даже если SQL-изменения только добавляют таблицы. Откат одного образа без проверки схемы недостаточен.
8. Файловая блокировка .env уже есть в env_config.py. При добавлении API нужно проверить совместное чтение/обновление OAuth тремя процессами и устаревшие credentials в памяти; наличие блокировки файла само по себе не доказывает корректность всей последовательности обновления.

Это требования к будущей реализации, а не утверждение о том, что перечисленные доработки уже выполнены.

## 3. Неизменяемые правила продукта

| ID | Правило для обоих каналов |
|---|---|
| R-01 | Допуск вручную; Telegram ID — идентификатор и источник прав. Username — контакт, а не роль |
| R-02 | Показывать только опубликованное время на ближайшие 7 суток; старт строго раньше now + 7 суток, как в rules.py. Вся встреча помещается в опубликованный интервал |
| R-03 | Длительности 30/45/60/90 минут; шаг начала 15 минут. Для Zoom — только 30, для Телемоста — все перечисленные; это сохраняемое правило проекта |
| R-04 | Между встречами и относительно занятости Google — минимум 30 минут; ровно 30 допустимо |
| R-05 | До встречи минимум 2 часа. Дополнительно срок решения должен быть не позже start − 2 часа; одной проверки «старт через 2 часа» недостаточно |
| R-06 | Решение — 3 рабочих часа в настроенном графике рассмотрения. Ночью и вне графика отсчёт приостанавливается. Расписание рассмотрения и дни доступности — разные сущности |
| R-07 | Среда, суббота, воскресенье закрыты по умолчанию; открываются только явным исключением на конкретную дату |
| R-08 | Выбранный слот удерживается 10 минут после успешной серверной операции. Просмотр слотов и ввод до выбора времени не резервируют место. Сохранение поля, перезагрузка и повторный запрос не продлевают удержание |
| R-09 | После подачи удержание действует до решения/истечения. Согласие администратора переводит заявку в ожидание ссылки, но ещё не подтверждает встречу |
| R-10 | Ссылка выбранного сервиса вводится вручную до срока решения. Подтверждение допустимо только после проверенного события Google с приглашённым email |
| R-11 | Ожидающую заявку посетитель может отменить. Подтверждённую — при now ≤ start − 1 час. В точности за час отмена разрешена; позже недоступна |
| R-12 | Отмена подтверждённой встречи завершается только после удаления/подтверждённого отсутствия события Google. До этого сохраняются занятость и состояние проверки |
| R-13 | Обязательны обращение, текущий Telegram username, email, новая цель встречи; телефон необязателен. При повторе контакты подтверждаются или редактируются |
| R-14 | Заявка хранит снимок контактов и шаблона на момент подачи. Изменение профиля или шаблона не переписывает старые заявки |
| R-15 | Закрытие времени и блокировка пользователя не отменяют встречи автоматически; администратор видит затронутые заявки |
| R-16 | Напоминания посетителю за 24 и 2 часа, если встреча подтверждена достаточно рано. Уведомления администратора — только Telegram; приглашение гостю по email — Google Calendar |
| R-17 | Профиль — до 2 календарных месяцев после последнего использования; завершённая заявка — до 2 календарных месяцев после завершения. Активный жизненный цикл сохраняется; это не 60 суток |
| R-18 | Посетитель не получает названия, описания, участников, идентификаторы и исходные ответы личных событий Google; API отдаёт только допустимые варианты записи |

Время определяет сервер. Хранение — существующие UTC Unix seconds; API передаёт даты-время в ISO 8601 с Z и отдельный IANA time_zone. В интерфейсе явно показывать часовой пояс расписания, по умолчанию Europe/Moscow, а не автоматически заменять его поясом устройства. Изменение часов рассмотрения применяется к новым расчётам; уже записанный decision_deadline_at не пересчитывается молча. Поддержку изменения самого часового пояса вынести в D-06.

## 4. Роли, интерфейс и функциональное покрытие

### 4.1. Вход и навигация

Основной вход: кнопка «Открыть приложение» в личном чате бота; дополнительно кнопка меню. Конкретное размещение согласуется в D-03. Прямая ссылка на Mini App может стать дополнительным входом после проверки сценария уведомлений. Информационная страница и обычные команды чата сохраняются.

Telegram предоставляет initData для серверной проверки; initDataUnsafe нельзя считать доверенным. Для основного входа выбрать поддерживающие нужные данные меню/inline-кнопку; обычная reply-keyboard Web App имеет другие ограничения. SDK предоставляет тему, safe area и события изменения окна. Эти особенности сверены с [документацией Telegram Mini Apps](https://core.telegram.org/bots/webapps). Все последующие сроки сессии и требования к интерфейсу — проектные решения этого ТЗ.

При открытии вне Telegram или без проверяемых данных показывать только сообщение «Откройте приложение из @MyMeetPlanning_bot» и переход к боту. Отладочный вход по произвольному ID в рабочей среде запрещён. Параметр ссылки может выбирать экран после авторизации, но не давать роль или доступ к чужой заявке.

Навигация посетителя: «Записаться», «Мои заявки», «Мои данные». Администратору — «Заявки», «Доступ», «Расписание», «Настройки» со сводкой и предупреждениями. Администратор не становится автоматически допущенным посетителем при переключении режима.

### 4.2. Сценарии посетителя

| ID | Экран/действие | Поведение и результат |
|---|---|---|
| V-01 | Первое открытие | Назначение, политика, отдельное действие согласия и «Запросить доступ»; посещение страницы само по себе не означает согласия |
| V-02 | Ожидание допуска | Статус запроса, «Обновить», переход в чат; слоты и чужие данные недоступны |
| V-03 | Отклонённый/заблокированный | Понятный статус; отклонённый может повторить запрос по действующему request_access; заблокированный не обходит блокировку новым входом |
| V-04 | Выбор встречи | Активный шаблон с описанием, длительность, платформа; несовместимый выбор требует корректировки до выбора времени |
| V-05 | Календарь | Ближайшие 7 суток и список стартов выбранного дня; видны только доступные варианты. Пустой день отличается от ошибки загрузки |
| V-06 | Удержание | После выбора сервер резервирует слот; показываются срок удержания и обратный отсчёт. При конфликте — обновить календарь и выбрать заново |
| V-07 | Контакты | Имя, email, необязательный телефон, username только для чтения, новая цель. Для повторного посетителя — «Использовать эти данные»/редактирование отдельных полей |
| V-08 | Согласие и проверка | Актуальная версия согласия, итог даты/пояса/длительности/платформы/контактов/цели, срок решения и отмены; отдельное «Отправить заявку» |
| V-09 | Результат подачи | Номер и «Ожидает решения», срок; не писать «Встреча подтверждена» до Google. Повторное нажатие возвращает ту же заявку |
| V-10 | Мои заявки | Активные и завершённые в пределах хранения, пагинация, карточка, статус и доступные действия. Ссылку подключения показывать только владельцу подтверждённой встречи |
| V-11 | Отмена | Экран подтверждения с датой и номером. Для подтверждённой — сначала «Запрос на отмену принят», затем фактический результат Google |
| V-12 | Мои данные | Просмотр/исправление контактов, удаление сохранённых контактов, отзыв согласия, ссылка на порядок обращения к оператору |
| V-13 | Возврат после закрытия | Прочитать серверное состояние. Неотправленную форму продолжить только при живом удержании; истёкшее время выбирать заново |

Если username отсутствует, показать инструкцию установить его в Telegram и заново открыть приложение для получения свежих подписанных данных. Нажатие «Проверить снова» не должно доверять отредактированному клиентом username или считать старую строку initData свежим профилем.

При удалении контактов объяснить: сохранённые контакты удаляются, история и активные обязательства обрабатываются по существующим срокам; это не удаление всех следов в Telegram/Google. Отзыв согласия запрещает новую подачу без нового согласия, но не отменяет уже созданную встречу. Очистить связанные контактные черновики во всех интерфейсах и не восстановить удалённое автосохранением старой формы.

### 4.3. Сценарии администратора

| ID | Раздел | Обязательные возможности |
|---|---|---|
| A-01 | Запросы доступа | Список ожидающих, карточка, разрешить/отклонить/заблокировать; списки разрешённых и заблокированных, возврат доступа через существующую модель статусов |

| A-04 | Видеоссылка | Ручной ввод, проверка HTTPS и домена выбранной платформы, запуск общей проверки/создания Google; при ошибке — сохранённое состояние и безопасный повтор |
| A-05 | Отмена | Подтверждение действия; для события Google дождаться согласованной отмены. Часовой лимит посетителя не переносится на администратора |
| A-06 | Расписание | Просмотр опубликованных интервалов, создание на дату, закрытие интервала/дня, ручное открытие закрытого дня |
| A-07 | Закрыть часть времени | block_time и unblock_time; снятие ручной блокировки не публикует заново закрытый исходный интервал |
| A-08 | Последствия изменения | До подтверждения закрытия показать предварительный список затронутых заявок; после операции — актуальный список. Ни одна встреча не отменяется скрыто |
| A-09 | Шаблоны | Создать/редактировать название, описание, инструкцию; скрыть/показать; снимки ранее поданных заявок неизменны |
| A-10 | Часы рассмотрения | Дни недели, несколько окон, валидация пересечений и непустого расписания; пример расчёта срока, предупреждение о применении к новым заявкам |
| A-11 | Сводка 7/30 дней | Запросы доступа, заявки, подтверждения, отказы, истечения, отмены, повторные записи, использование контактов, платформы и среднее время решения |
| A-12 | Предупреждения | Проблемы календаря/отмены, ошибки доставки, заявки без ссылки; переход к соответствующей заявке, безопасный повтор Google там, где он допустим |
| A-13 | Подключение Google | Только безопасный статус/последняя проверка и инструкция восстановления для владельца; OAuth и секреты не вводятся в Mini App |

Для сводки сохранить текущий смысл метрик из AdminFlow._stats: период по submitted_at, счётчики по текущему статусу, среднее время до действия awaiting_link/rejected в обычных минутах. Не выдавать его за рабочие часы или SLA и не внедрять новую аналитику под теми же названиями.

Формы используют календарь, выбор времени и полей вместо разбора текстовых команд. Параметры 2 часа/30 минут/3 рабочих часа и список длительностей остаются правилами продукта, а не произвольными настройками Mini App. Возможность менять эти константы требует отдельного изменения продуктового ТЗ.

### 4.4. Общее качество интерфейса

- Адаптация к Telegram Android, iOS, Desktop и Web; светлая/тёмная тема, экран от 320 CSS px без горизонтального скролла.
- Области вырезов и панели Telegram, экранная клавиатура и поворот устройства не перекрывают поля и основную кнопку. Совместимость новых SDK-возможностей проверяется; предусмотрен обычный интерфейс при их отсутствии.
- Метки полей, понятные ошибки у поля, фокус после ошибки, клавиатурная навигация; статус различим текстом, а не только цветом.
- «Назад» сохраняет допустимый введённый текст; изменение слота отдельно освобождает прежнее удержание. Закрытие WebView не считается гарантированным сигналом отмены: работает серверное истечение.
- На каждом экране различать загрузку, отсутствие данных, отказ в доступе, устаревшее состояние, сетевую ошибку и успех.
- Пока запрос выполняется, защитить кнопку от повторного нажатия; это удобство, серверная идемпотентность всё равно обязательна.
- При потере связи не объявлять успех, не отправлять накопленные изменения автоматически после восстановления; сначала получить текущее состояние.

### 4.5. Последовательность записи — уточнение после урока

**Согласовано пользователем:** короткий пошаговый сценарий; после просмотра и правок принято оформление и поручен следующий этап. Конкретный вариант отдельно не выбирался. Детали ниже служат baseline реализации и проверяются на рабочем UI в MA-3/MA-4; технологии приняты отдельным ответом D-01/D-02.

Предлагаемый порядок:

1. «Встреча»: выбрать активный шаблон, увидеть его краткое описание.
2. «Длительность и связь»: явный выбор длительности и доступной платформы на одном коротком экране. 30 минут не выбираются без действия посетителя. Несовместимый Zoom не скрывать после подачи: проверять сразу.
3. «Дата и время»: компактный список дат в пределах ближайших 7 суток и стартов выбранного дня; полная месячная сетка — альтернатива D-10. Дополнительный обязательный шаг «Неделя» для такого горизонта не нужен. Разрешённые дни могут пересекать границу недели; список не обрезается по воскресенью.
4. После успешного hold — «Контакты и цель»: подтверждение сохранённых данных либо поля для исправления; цель новой встречи обязательна. Отдельное согласие показывается самостоятельным действием согласно V-08. При необходимости разбить длинную форму на два коротких экрана без дополнительных полей.
5. «Проверка»: все значимые сведения, время/пояс, срок решения и отмены, явная кнопка «Отправить заявку».
6. «Заявка отправлена»: номер, фактический статус, переход в «Мои заявки»/чат.

Шаги 1–3 не резервируют время до успешного выбора конкретного старта. Показ экранов не создаёт заявку автоматически. Переход вперёд — по «Далее», если требуется подтверждение полей; не использовать автоматический переход после выбора карточки без согласования. Назад не отправляет заявку, не стирает контакты и не меняет срок удержания. Изменение шаблона/платформы/длительности после hold требует явной проверки и нового выбора времени, а не изменения занятого интервала только в браузере.

Новые поля «Тема» и «Комментарий» из урока не добавляются. Название карточки берётся из снимка шаблона, обязательная цель остаётся целью. Номер заявки появляется после создания серверного объекта и остаётся постоянным; в пользовательском результате подачи выводится «Заявка №…».

### 4.6. Карта экранов и содержание

| Экран | Что видно первым | Основное действие | Что вынесено глубже |
|---|---|---|---|
| Главная посетителя с допуском | Короткое название/назначение и кнопки «Записаться», «Мои заявки»; «Мои данные» доступно вторичным действием | Записаться | История, контакты, длинные описания; нет придуманной биографии/фотографии или пустого места под них |
| Главная без допуска | Назначение, политика, текущий статус доступа | Запросить доступ либо обновить ожидание | Приватные разделы и расписание недоступны |
| Шаг записи | Короткий заголовок, текущий шаг, выбранные ранее данные в компактном виде | Далее либо выбор доступного времени | Подсказки по запросу, без дублирующих рекламных блоков |
| Мои заявки | Компактные группы, ближайшие актуальные карточки | Открыть карточку | Полные контакты и история в раскрытии карточки/деталях |
| Карточка | Номер, шаблон, дата/время, пояс и понятный статус | Допустимая отмена или подключение | Сроки, контакты, цель, пояснение проблемы; нет внутренних ID и кода статуса |
| Админ-вход | «Заявки на решение» с числом, доступ к «Запросам доступа», «Настройкам» | Открыть ожидающую очередь | Сводка и технические сведения |
| Админ-очередь | Ожидающие заявки по ближайшему сроку решения | Открыть заявку, согласовать/отклонить | Остальные статусы через фильтр, без панели всех счётчиков на каждом экране |
| Настройки | Разделы «Доступ», «Опубликованное время», «Часы рассмотрения», «Шаблоны встреч», «Google Календарь», «Предупреждения», «Сводка» | Открыть нужный раздел | Формы редактирования на отдельных экранах; список заблокированных только внутри «Доступа» |

Это информационная структура, а не готовый визуальный макет. В MA-0V выбрать конкретное расположение навигации и деталей карточки. В административном режиме должно быть очевидно, где заявки посетителей для решения. «Мои заявки» не заменяет административную очередь и не показывает административные действия обычному пользователю.

**Группы посетителя, предложение D-10:** «На рассмотрении» (pending/awaiting_link), «Предстоящие» (confirmed и встреча ещё не завершилась), «История» (терминальные и прошедшие confirmed). creating_calendar/attention остаются в актуальной части с отдельной заметной пометкой до разрешения проблемы. held — продолжение формы по D-04, не поданная заявка. Внутри карточки всегда точный понятный статус из раздела 5.

Группы взаимоисключающие: проблемная active-заявка не прячется в истории только из-за прошедшего времени. Будущая подтверждённая встреча при now < ends_at остаётся предстоящей/текущей; при now ≥ ends_at отображается в истории без добавления статуса SQLite. Неподанные истёкшие holds не засоряют обычную историю заявок. Терминальные заявки сохраняются в пределах R-17, а не удаляются из интерфейса по примеру автора урока.

Сортировка: на рассмотрении — по decision_deadline_at, затем id; предстоящие — по starts_at, затем id; история — по времени завершения/окончания по убыванию, затем id. У администратора очередь «На решение» по deadline; проблемные заявки доступны заметным действием из очереди/предупреждений. Серверные фильтры и пагинация используют те же правила; UI не фильтрует только уже загруженную первую страницу.

### 4.7. Визуальные критерии и тексты

**Пожелание пользователя 10.10.2026:** ориентироваться на предоставленный Pinterest-референс: глубокий тёмно-синий фон, голубые световые акценты, мягкие градиенты, скруглённые карточки и светлая читаемая типографика. Разбор и предложения для макетов — в [визуальном направлении](mini_app_design_direction.md), исходный скриншот сохранён вместе с документацией. Конкретные макеты, точные токены цветов/шрифтов и светлая адаптация ещё согласуются в MA-0V.

Интерфейс сохраняет короткий пошаговый сценарий и компактность: крупные 3D-сцены, длинная рекламная обложка, наклонённые/перекрывающиеся рабочие карточки и фоновое видео из характера референса не являются обязательными элементами. Цвета панелей Telegram должны сочетаться с выбранной темой. Использовать рабочее название бота до отдельного выбора названия; фотография, логотип и биография — только из предоставленных/утверждённых материалов.

- На главной при ширинах 320/360/390/430 CSS px и контрольной видимой высоте 568 px заголовок и основные действия достижимы без прокрутки пустого декоративного блока. Обязательный текст согласия не урезается ради этого условия.
- Отступ сверху обусловлен safe area и навигацией, а не пустой «обложкой». На каждом эталонном экране проверяется суммарная высота заголовка, панели и отступов; слово «адаптивно» без просмотра результата недостаточно.
- Никакие подписи, кнопки, фильтры и края карточек не обрезаются на узком экране. Строки слотов/длительностей переносятся предсказуемо; нажатие не требует попадать в край за экраном. Рабочий ориентир области нажатия — минимум 44 × 44 CSS px, без увеличения высоты всех карточек до больших баннеров.
- Не создавать длинную горизонтальную ленту всех технических статусов. Компактная группировка/меню фильтра должны показывать, что есть другие группы, и быть доступны с клавиатуры.
- Один заголовок на текущую задачу; не повторять «Новая заявка», «Комментарий необязателен» в нескольких блоках. Не выводить служебные слоганы вроде «Пошаговая запись без лишнего текста», демонстрационные роли, технические объяснения архитектуры.
- Часовой пояс виден компактно в расписании, карточке и итоговой проверке; он не дублируется отдельными баннерами. Убирать его совсем по примеру урока нельзя.
- «Назад», «Сбросить выбор» и «Выйти» имеют разный смысл. Сброс действует реально, с подтверждением при потере данных/освобождении hold. Закрытие не гарантирует мгновенного освобождения слота; об этом сообщать кратко в подходящем месте.
- «Далее» активируется для корректного ввода и объясняет недостающие поля. Не блокировать валидный email из-за отличающейся клиентской регулярной проверки; trim и правила согласованы с общим серверным валидатором.
- Основная кнопка не перекрывается экранной клавиатурой/панелью Telegram. При крупном системном шрифте допустима прокрутка, но не исчезновение действия.
- Видеоссылку отображать понятной кнопкой «Подключиться», не длинной строкой с секретными параметрами; хранение и разрешённый адрес не изменяются.

| Техническое понятие | Пользовательский текст/пояснение |
|---|---|
| pending | Ожидает решения |
| awaiting_link | Ожидает ссылку от администратора |
| attention | Требует проверки; указать отдельно, подтверждение или отмена ещё не завершены |
| blacklist | Заблокированные пользователи |
| lead time | Минимальный срок до встречи — 2 часа; параметр не становится редактируемым без изменения ТЗ |
| gap/buffer | Перерыв между встречами — минимум 30 минут |
| availability | Опубликованное время для записи |
| review windows | Часы рассмотрения заявок; именно в них считаются 3 рабочих часа |
| refresh token | В обычном интерфейсе не показывать; объяснять необходимость повторно подключить календарь только при подтверждённой проблеме |

Окна рассмотрения можно задавать отдельно для каждого дня и несколькими интервалами — это существующая модель. Опубликованное время задаётся на конкретные даты. Автоматически повторяющееся недельное расписание записи не появляется из-за похожей формы в уроке; отдельное расширение требует описания новых правил и согласования.

### 4.8. Проверка интерфейса до основной разработки

В план добавляется MA-0V: до основной реализации подготовить согласуемые макеты главной, выбора времени, контактов, итоговой проверки, «Моих заявок», админ-очереди и настроек. 10.10.2026 по поручению пользователя подготовлены два презентационных варианта и 20 основных экранов; [протокол просмотра](design/ma-0v-review.md) содержит проверки и открытые решения. Конкретный вариант ещё не принят. Референс должен сопровождаться пояснением, что именно берём: цвет, плотность, форма карточки; чужие данные/брендинг не копируются автоматически.

Позже, после разрешения реализации, исполнитель сам подготавливает локальную ссылку просмотра и проверяет, что она открывается. Статический демонстрационный просмотр использует синтетические fixtures, не рабочую SQLite, токены или административный обход auth. Он проверяет внешний вид, а не Telegram-аутентификацию. Настоящие интеграционные проверки проводятся в тестовом Telegram WebView уже после появления auth/API.

Для каждого дефекта фиксировать экран, роль, шаг, размер окна, действие, ожидаемый/фактический результат и подтверждение исправления. Исполнитель воспроизводит проблему и проверяет после исправления на том же размере, затем проверяет соседние экраны. Не переносить обязательный дефект текущего этапа в абстрактную «полировку». Если дефект добавлен после завершения этапа, вернуть его в «В работе» либо открыть явно связанный корректирующий пункт.

Владельцу выдаются кликабельная проверенная ссылка, 3–7 действий по кнопкам, ожидаемый результат и что сообщить при отклонении. Не требовать запускать команды и разбираться в логах. Если доступная среда не позволяет исполнителю выполнить проверку, записать ограничение и конкретный ручной сценарий вместо утверждения «всё проверено». Установка инструмента из учебного примера не является обязательным шагом.

### 4.9. Понятный статус Google Календаря

«Есть OAuth-настройки», «время access token истекло» и «календарь сейчас доступен» — разные состояния. Отображаемый статус строится по реальному результату проверки, checked_at и безопасному коду ошибки, не по одному наличию .env или дате токена.

| Состояние UI | Основание | Доступное действие |
|---|---|---|
| Ещё не проверено | Нет результата успешной/неуспешной проверки в этом контуре | Проверить подключение |
| Работает | Успешный безопасный запрос занятости, время последней проверки | Проверить повторно по необходимости |
| Временно недоступно | Сетевая ошибка/тайм-аут | Повторить проверку позже; не предлагать бронирование как будто календарь свободен |
| Нужно подключить заново | Общая интеграция вернула auth_expired/подтверждённую ошибку авторизации | Понятная инструкция владельцу и предупреждение в Telegram |
| Нет прав на календарь | Проверка отказана из-за разрешений | Инструкция проверки выбранного календаря/доступа; не выдавать токены |
| Последняя проверка устарела | Возраст результата больше согласованного порога | Показать время и предложить новую проверку, не называть его актуальной гарантией |

Предварительный порог устаревания — 5 минут, уточняется в D-07; не запускать дорогостоящий Google-запрос при каждом рендере. Отдельное админ-действие проверки ограничить по частоте, использовать существующий Google-клиент. Автообновление OAuth выполняется сервером; UI не просит пользователя вручную обновлять токен при обычном истечении access token. Нельзя обещать, что повторное разрешение владельца никогда не понадобится.

Кнопка проверки ведёт к результату Google, а не в чужой раздел меню. Успех/ошибка отображаются в том же разделе; критическое предупреждение идёт через текущую очередь, с защитой от повторного спама. Не показывать ошибку подключения как «успешно» только потому, что HTTP-запрос принят.

## 5. Общие состояния и совместимость каналов

### 5.1. Отображение статусов

Новые названия экранов не создают новую машину состояний.

| Код SQLite/API | Текст | Основной смысл/следующий шаг |
|---|---|---|
| held | Заполнение заявки | Удержание до hold_expires_at; submit → pending, отказ от формы/TTL → expired |
| pending | Ожидает решения | Решение администратора, отмена посетителя/администратора или истечение |
| awaiting_link | Ожидает ссылку | Согласие администратора получено; до deadline нужна ссылка; возможны отмена/истечение |
| creating_calendar | Создаётся в календаре | Выполняется/восстанавливается операция Google; не показывать финальный успех |
| confirmed | Подтверждена | Событие проверено; доступны ссылка и разрешённая отмена |
| rejected | Отклонена | Время освобождено |
| expired | Срок истёк | Удержание/заявка больше не действует; выбрать новое время |
| cancelled_by_visitor | Отменена посетителем | Финальная отмена |
| cancelled_by_admin | Отменена администратором | Финальная отмена |
| attention | Требует внимания | Проверить причину: создание/сверка Google либо отмена с cancel_requested_at; нельзя трактовать как освобождённое время |

Сервер возвращает allowed_actions, причину внимания, сроки и revision. allowed_actions помогает UI, но не заменяет серверную проверку при команде. «Завершена по времени» может быть группой списка для прошедших встреч, но не новым хранимым статусом без миграционного решения. На точной границе decision_deadline_at новое согласование/ввод ссылки недопустимы.

### 5.2. Межканальные требования

1. Созданная в Mini App заявка видна и обрабатывается в чате с тем же номером; заявка из чата видна в Mini App. Согласование, отмена, блокировка и изменение настроек сразу меняют общие данные.
2. Mini App обновляет активную карточку при возврате в окно и после команды; предлагаемый polling раз в 10 секунд только на видимом экране. Нет необходимости в WebSocket для первой версии. В фоне опрос останавливается; «Обновить» доступно вручную.
3. Устаревшие кнопки чата и формы браузера не меняют уже принятый результат. При конфликте сервер возвращает текущее состояние и просит перечитать карточку.
4. Идемпотентность команды в HTTP не заменяет общую защиту в сервисе: чат не знает HTTP-ключей и всё равно должен участвовать в атомарной проверке перехода.
5. Отказ API или статики не должен останавливать polling-бот и worker. Отключение Mini App не должно лишать пользователя существующих чат-сценариев.

**Черновики — принятое решение D-04:** один активный черновик бронирования на посетителя для двух интерфейсов. При переходе предложить «Продолжить» или «Сбросить и выбрать заново»; нельзя автоматически создавать второй hold или стирать форму в другом канале. Для этого потребуется общий сервис черновиков с ревизией и адаптация chat flow. Команда «В меню» в чате не должна неожиданно освобождать слот, редактируемый в Mini App. Принятие/сброс и обновление формы проверяются транзакционно. Ограничение относится к незавершённой форме, не к числу поданных заявок пользователя. Альтернатива и объём согласования — раздел 14.

Админ-формы Mini App не используют admin_dialogs как собственное состояние. Результаты сохраняются через общий сервис; admin_dialogs продолжает хранить шаг чата. Одновременные сохранения шаблона/часов или разные видеоссылки к одной заявке должны дать конфликт, а не незаметное затирание данных.

## 6. Архитектурные требования

Предлагаемая схема:

~~~text
Telegram chat → aiogram / chat flows ────────┐
                                           ├→ общие сценарии и проверки
Telegram Mini App → HTTPS API / auth ───────┘       │
                                     rules + BookingService + queries/drafts
                                                   │
                          одна SQLite ←→ задания/уведомления ←→ worker
                                                   │
                          calendar_flow → GoogleCalendar → Google Calendar
~~~

API — адаптер: проверяет формат/аутентификацию, создаёт доверенного actor, вызывает общий сценарий и формирует ограниченный ответ. Репозитории и SQL-запросы располагаются в общем Python-пакете. Браузер не подключается к SQLite, Telegram Bot API с токеном или Google Calendar API.

Два транспортных процесса могут напрямую использовать один пакет и одну SQLite на одном VPS; необязательно переделывать чат так, чтобы он ходил в собственный HTTP API. Бизнес-правила должны быть едиными независимо от выбора транспорта. Нельзя копировать расчёт слотов и статусов в frontend или отдельный Node backend.

Действия с Google и Telegram выполняются вне блокирующих транзакций SQLite. Для текущих синхронных Google-вызовов и sqlite3 предусмотреть ограниченный пул выполнения/эквивалентный механизм, чтобы они не блокировали весь HTTP-сервер. Размер пула и число процессов подбираются по измерениям, без предположения о неограниченной параллельности на VPS 1 ГБ.

Чтение слотов и создание hold запрашивают актуальную занятость Google; перед submit и подтверждением — повторная проверка через существующий calendar_flow. Ошибка FreeBusy не означает свободный календарь. Источник прав, настроек и server_time всегда сервер.

Возобновление создания Google после падения API должно быть определено: существующая админ-команда безопасного повтора остаётся обязательной; если вводится автоматическое восстановление, использовать существующую сохраняемую очередь с общим захватом задания. Не запускать второй несогласованный цикл повторного создания.

## 7. Telegram-аутентификация и сессия

### 7.1. Проверка подлинности

Клиент передаёт исходную строку Telegram.WebApp.initData в тело POST /api/v1/session по HTTPS. Сервер проверяет её до использования user. Для HMAC-проверки: исключить hash, отсортировать остальные полученные пары, соединить key=value через LF; секрет HMAC-SHA256 получить с ключом WebAppData и сообщением bot_token, затем вычислить HMAC строки и сравнить с hash. Поля, включая signature при её наличии, обрабатывать по алгоритму HMAC, не смешивая его с отдельной схемой Ed25519. Проверять auth_date. Основание — [официальный алгоритм Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Требования проекта к проверке:

- Строго разбирать query string; отклонять дубли ключей, некорректное кодирование, отсутствующие обязательные поля, неверные типы и слишком большой ввод. Не пересобирать JSON user перед проверкой подписи и не декодировать данные повторно.
- Сравнивать подпись за постоянное время. Использовать только серверный токен именно этого бота; другой бот/тестовая среда не должны проходить проверку.
- Требовать проверенный user.id, хранить его без 32-битного усечения. В JSON API передавать Telegram ID строкой; actor_id никогда не брать из тела бизнес-команды.
- Принятые D-07: возраст initData не более 5 минут, отклонение auth_date в будущее не более 30 секунд. Это настройки проекта D-07, принятые владельцем 11.10.2026, не ограничения, объявленные Telegram.
- query_id может отсутствовать; не делать его единственным ключом личности или защиты повторов. start_param, chat_instance, username, first_name и параметры URL не назначают права администратора.
- Согласие на персональные данные, ручной допуск и аутентификация — три разные проверки. Успешная Telegram-аутентификация не открывает слоты автоматически.

### 7.2. Принятая модель сессии — D-07

Принята короткая серверная сессия: случайный непрозрачный bearer не менее 256 бит, только в памяти страницы, передаваемый через Authorization. В SQLite хранить лишь криптографический хеш bearer, Telegram ID, время выдачи/окончания, признак отзыва и минимальный проверенный username для снимка заявки; без полного Telegram user JSON. Метаданные удаляются по TTL сессии. Сам bearer не писать на диск, в URL, localStorage, sessionStorage, Telegram storage или журналы. Постоянные ключи приложения остаются только в защищённом .env; новые сессионные идентификаторы не превращаются в дополнительные файлы с секретами.

Принятый абсолютный срок — 30 минут, без бесконечного продления открытой вкладкой. После истечения — 401 и предложение переоткрыть Mini App с новыми initData; серверный черновик живёт только в собственных сроках. При выходе сессия отзывается. Отдельные требования к cookie-сессии, если она будет выбрана вместо bearer: Secure, HttpOnly, подходящий SameSite с проверкой Telegram Web, CSRF-токен и проверка Origin. Не смешивать две модели без обоснования.

Защита повторного обмена: сохранять отпечаток проверенной канонической строки вместе с подписью до конца окна её допустимости; повторная выдача новой сессии по той же строке запрещена. Если ответ на обмен потерян и клиент не получил bearer, показать необходимость переоткрыть приложение. Проверить этот сценарий на реальных клиентах; не обходить его постоянным разрешением replay. Такая мера ограничивает повторное использование, но не заменяет предотвращение утечки initData.

Текущий статус доступа и права администратора проверяются на каждом запросе, а не копируются навсегда в сессию. После блокировки уже выданная сессия не позволяет ни смотреть слоты, ни создать удержание/подать заявку. Удаление контактов или отзыв согласия не должны уничтожать доказательство роли и позволять обойти ограничения доступа.

### 7.3. Уведомления и первый контакт с ботом

Базовый путь начинается из личного чата, где пользователь нажал «Начать». Для дополнительного прямого входа предусмотреть отдельный шаг открытия чата/получения разрешения на сообщения, если оно требуется: открытие Mini App само по себе не считать доказательством, что бот может писать пользователю. Состояние возможности доставки отделить от допуска к записи.

Ошибка доставки не отменяет встречу автоматически. Статус можно получить из API, а существующая очередь фиксирует ошибку и повторяет отправку по своим правилам. Не обещать доставку Telegram-сообщения или приглашения Google только по успешному HTTP-ответу.

## 8. Контракт API — локальная реализация MA-2

Пути ниже реализованы локально на принятом FastAPI; точные DTO/параметры — [OpenAPI](mini_app_openapi.json). Реальный Telegram/HTTPS ещё не проверен. Корень /api/v1. Любая приватная операция требует сессию; админ-пути — дополнительно серверную проверку ID владельца. Списки используют cursor и limit (по умолчанию 20, максимум 100, стартовые настройки D-07). GET не выполняет бизнес-команды.

### 8.1. Общие ответы и поля

- Успех: data, server_time, request_id; для списков — next_cursor. Запись содержит id, status, revision и allowed_actions по необходимости.
- Ошибка: error.code, безопасное русское error.message, field_errors при ошибках формы, request_id, retryable. Никаких stack trace, SQL, токенов и исходных исключений Google.
- Бронирование посетителя: id, starts_at, ends_at, time_zone, duration_minutes, video_service, снимок шаблона/его контактов, purpose, status, hold_expires_at, decision_deadline_at, cancel_until, разрешённая видеоссылка, понятное состояние синхронизации. Скрыть внутренние Google event/calendar ID, lease задания, служебные payload и чужие контакты.
- Bootstrap: роль, access_status, текущий username, версия/ссылка политики, допустимые длительности по платформе, time_zone, server_time, capability flags, безопасная конфигурация UI. Не передавать .env или полный app_settings.
- Слот: starts_at, ends_at, time_zone, interval_id либо непрозрачный slot_ref, checked_at. Любой идентификатор повторно разрешается и проверяется сервером; наличие slot_ref не гарантирует бронь.
- Времена клиента не определяют now, deadline, роль, статус, получателя уведомления или владельца заявки. Поля неизвестного назначения в изменяющих DTO отклоняются.

API не предоставляет метод произвольного SQL, изменения status, вызова любого worker job, чтения файла логов, редактирования секретов или исполнения системной команды.

### 8.4. Повторы, конкуренция и долгие операции

**Idempotency-Key** обязателен для изменяющих бизнес-команд, включая создание hold, подачу, решение, ссылку, отмену, создание интервала/шаблона и удаление данных. Область ключа: actor + команда/маршрут + key. Сохранять отпечаток нормализованного запроса, безопасную ссылку на результат и состояние операции в общей базе, а не в памяти одного HTTP-процесса.

Одинаковый ключ и тот же запрос возвращают тот же объект/результат без повторного эффекта; тот же ключ с другим содержимым — 409 IDEMPOTENCY_CONFLICT. Перед повторной выдачей результата снова проверить права и наличие данных: идемпотентность не должна возвращать удалённые контакты или обходить блокировку. Не сохранять бессрочные копии response с персональными данными. Принятое хранение ключа — 24 часа; после удаления ключа бизнес-инварианты и идентификатор заявки всё равно защищают от повторного подтверждения и события Google.

Не только HTTP-ключ, но и изменения заявки/задания/уведомления должны коммититься согласованно. Два процесса, одновременно впервые увидевшие ключ, не могут оба выполнить действие. При падении между внешним вызовом Google и записью результата продолжать сверку по зарезервированному event_id. Состояние «выполняется» должно иметь восстановление/ограниченную аренду, чтобы crash не заблокировал команду навсегда.

Для редактируемых объектов использовать монотонную revision и If-Match либо expected_revision в DTO. Текущее updated_at с точностью до секунды не гарантирует обнаружение двух записей в одну секунду. Общий сервис, включая чат, обновляет и проверяет ревизии; stale → 409 STATE_CHANGED. Атомарность переходов и защита пересечения обязательны даже при отсутствии UI-ревизии в старой кнопке чата.

Долгая операция может вернуть 202 с booking_id/operation_id только после устойчивой записи принятого действия. Нужен GET /operations/{id} с проверкой владельца/администратора, если выбран operation_id; при варианте booking_id клиент перечитывает карточку. 202 не означает confirmed. При тайм-ауте клиент сначала узнаёт состояние, затем повторяет с прежним ключом. В MA-2 выбран синхронный вызов с устойчивым намерением/lease; параллельный повтор получает 202. После сбоя/рестарта тот же ключ продолжает сверку прежнего события.

### 8.5. Ошибки и реакция интерфейса

| HTTP / code | Значение | Действие |
|---|---|---|
| 400 INVALID_REQUEST | Некорректный формат/неизвестные поля | Показать ошибку формы, не повторять автоматически |
| 401 AUTH_INVALID / SESSION_EXPIRED / AUTH_REPLAY | Неверная подпись/сессия/повтор обмена | Открыть Mini App заново |
| 403 ACCESS_PENDING / ACCESS_BLOCKED / ADMIN_REQUIRED | Недостаточно прав | Обновить экран доступа, очистить приватное состояние UI |
| 404 NOT_FOUND | Объект отсутствует или чужой | Одинаковый безопасный ответ, без раскрытия владельца |
| 409 SLOT_UNAVAILABLE / STATE_CHANGED | Слот занят, настройки/состояние изменились | Перечитать состояние и предложить выбор |
| 409 IDEMPOTENCY_CONFLICT | Повтор ключа с иным телом | Не отправлять второй эффект, показать необходимость обновить действие |
| 410 HOLD_EXPIRED | Срок формы истёк | Освободить выбор в UI, выбрать слот заново |
| 422 VALIDATION_ERROR / POLICY_REQUIRED / CANCELLATION_TOO_LATE | Правило продукта/поле не выполнено | Пояснить конкретное ограничение |
| 429 RATE_LIMITED | Превышен лимит | Retry-After, без цикла мгновенных повторов |
| 503 STORAGE_BUSY / CALENDAR_UNAVAILABLE | Временная недоступность | Безопасный повтор после чтения состояния; не показывать свободные слоты при ошибке Google |
| 500 INTERNAL_ERROR | Непредвиденная ошибка | Короткий текст и request_id для диагностики |

Если при ошибке операция уже сохранена в creating_calendar/attention, вернуть/позволить получить этот факт. Ошибка HTTP и бизнес-состояние — разные вещи. Не сообщать «ничего не произошло», когда ответ Google мог потеряться.

## 9. Безопасность, персональные данные и эксплуатационные пределы

### 9.1. Защита данных и интерфейсов

- HTTPS для статики и API. Предпочтительно один origin: отдельные пути /app/ и /api/, корень текущего сайта и политика сохраняются. Другой поддомен — вариант D-03 с явным CORS allowlist.
- Для bearer-модели принимать изменяющие запросы как JSON с Authorization; запретить wildcard CORS и отражение произвольного Origin. Origin/CORS — дополнительная граница браузера, не способ аутентификации.
- Экранировать текст шаблонов, имени, цели и сообщений; не исполнять HTML пользователя. CSP с минимальным набором источников и Telegram SDK; frame-ancestors проверить с Telegram Web, не ставить запрет встраивания без теста реального клиента.
- Видеоссылка — существующая общая проверка: HTTPS; telemost.yandex.ru либо zoom.us/его поддомены, порт отсутствует или 443, без userinfo, с непустым path. Отвергать поддельные суффиксы домена. Не загружать ссылку на сервере для предпросмотра: это добавило бы SSRF и утечку секрета подключения.
- Поля посетителя: до 500 символов на текст по текущему flow; телефон соответствует общей проверке PHONE_PATTERN либо пустой; email — существующей проверке. Шаблон: название до 100, описание/инструкция до 500; видеоссылка до 1000. Общая валидация должна одинаково применяться к чату и API.
- Лимит тела JSON, предлагаемый к проверке: 16 КиБ. Лимиты диапазона слотов, пагинации и числа запросов контролируются сервером, без загрузки всей истории одним ответом.
- Персональные ответы, сессия и API: Cache-Control: no-store. Не использовать service worker/offline cache для контактов и заявок. Статические файлы с хешем можно кешировать отдельно.
- Секреты Telegram/Google только в локальном и серверном .env; не включать их в frontend build, Git, образ, тестовые fixtures или логи. Тестовые ключи генерировать в памяти. Не читать/копировать рабочие секреты ради подготовки документации.
- Не отдавать .env, SQLite, WAL/SHM, исходные конфигурации и закрытые логи через nginx. Права API на диск ограничить необходимыми каталогами; публичный контейнер статики не получает базу и .env.
- Право владельца объекта проверять для всех id, включая holds, drafts, bookings, operations и idempotency records; непредсказуемые ID не заменяют проверку доступа.

### 9.2. Лимиты и защита от удержания всех слотов

Предлагаемые стартовые значения D-07: обмен сессии до 10/мин/IP, чтения до 60/мин/сессия, изменения до 20/мин/Telegram ID, создание нового удержания до 6/мин/Telegram ID. Учесть общий IP пользователей; роль/допуск не заменять IP-адресом. Лимиты общие для HTTP-процессов и сохраняют действие при обычном рестарте; инфраструктура без Redis допустима.

Политика одного активного черновика и ограничение новых holds должны применяться общим слоем, иначе смена канала обойдёт защиту. Точный допустимый темп обычной работы измерить и согласовать; ограничения не должны мешать админу обрабатывать нормальную очередь. Возвращать 429, не создавать частично записанные команды.

### 9.3. Хранение и удаление

Существующие сроки R-17 сохраняются. Сессии, использованные auth-digest и ключи идемпотентности имеют отдельные короткие TTL и очищаются существующим worker или согласованным общим заданием. Хранить минимум: хеши и ссылки, а не копии контактов. Пассивный polling списка не должен бесконечно продлевать last_used_at: определить значимое действие пользователя и проверить согласованность с чатом.

Политика и согласие показывают одну утверждённую версию в обоих каналах. Повышение версии не объявляет прежнее согласие новым. Отзыв проверяется перед submit, включая форму, которая уже была открыта. При выходе, отзыве доступа и удалении контактов очистить приватное клиентское состояние.

Никакие данные не передаются внешней аналитике или сервису записи сессий по умолчанию. Сохранить существующую схему передачи email в Google и Telegram-уведомлений; расширение схемы обработки описать и согласовать перед использованием с клиентами. Правовая проверка из MVP остаётся отдельной открытой зависимостью.

### 9.4. Логи, диагностика, доступность

Логировать время, компонент, request_id, действие, безопасный ID заявки, результат, длительность и код ошибки. Не писать initData, Authorization, cookie, токены, имя/email/телефон, цель, тело запросов, видеоссылки, данные Google или полный ответ исключения. Это касается также nginx access/error logs, HTTP middleware, frontend telemetry и ошибок валидации выбранного фреймворка.

Минимальные метрики: ошибки/латентность API, число 409/429/503, ожидание блокировки SQLite, возраст задач, ошибки Google/Telegram, размер журналов и диска. Метрики не содержат контактов. Критические предупреждения используют текущую Telegram-очередь с дедупликацией; внешний платный мониторинг не вводится.

Предложение для приёмочного профиля нагрузки D-08: 20 одновременно открытых клиентов в течение 15 минут, чтение локальных данных p95 ≤ 1 с, ответ интерфейса на нажатие ≤ 200 мс, первоначальный полезный экран ≤ 3 с при фиксированных условиях сети 10 Мбит/с и RTT 100 мс. Google-зависимые операции измеряются отдельно: показывать прогресс сразу, конечный результат или сохранённое состояние проверки — без бесконечного ожидания. Зафиксировать общий серверный тайм-аут и ограничение числа последовательных Google-вызовов после выбора API; один существующий вызов имеет timeout 15 с, а сценарий может включать несколько.

При целевой нагрузке: ни одной двойной брони, утечки или ложного подтверждения; отсутствие OOM/restart-loop, сохранение работы чата/worker, контролируемые очереди и журнал. На текущем VPS 1 ядро/1 ГБ/10 ГБ это нужно измерить; документация не гарантирует достаточность ресурсов.

## 10. Целостность бронирования и внешние сбои

1. Любой hold и изменение активной занятости выполняются с общими короткими BEGIN IMMEDIATE и существующими триггерами пересечения. В активную занятость входят held, pending, awaiting_link, creating_calendar, confirmed, attention. Истёкший hold освобождается общей логикой, а не только исчезает из браузера.
2. Проверка прав, текущего статуса, допустимого перехода и запись результата выполняются в одной транзакционной границе. Общие сценарии должны защищать также разные одновременные команды: approve против cancel, submit против expire, разные ссылки, закрытие интервала против submit.
3. SQLite busy_timeout уже ограничен (по умолчанию 3000 мс). При исчерпании ожидания — понятная повторяемая ошибка, без 500 со строкой SQL и без частичной записи.
4. Рабочая SQLite одна: /opt/meeting-bot/data/bot.sqlite. Бот, API и worker на одном VPS работают с тем же локальным каталогом, включая WAL/SHM. Запрещены рабочая копия базы только для Mini App и размещение WAL на сетевом диске.
5. Проверка Google вне транзакции не делает Google и SQLite единой транзакцией. Пользователь может вручную занять календарь одновременно с подтверждением; абсолютную защиту от такого внешнего изменения обещать нельзя. Нужны повторная сверка, attention и предупреждение при обнаружении расхождения. Если планируется автоматическое обнаружение внешних правок уже подтверждённых встреч, его периодичность/задание нужно отдельно описать: текущая проверка исходников не доказывает наличие постоянной синхронизации всех событий.
6. Сохранить общий зарезервированный google_event_id, связь booking_id в событии, проверку времени и приглашённого email. Не генерировать новое событие при каждом HTTP-повторе. При тайм-ауте сначала выяснить, создано ли прежнее событие.
7. Сбой API после события Google, но до ответа клиенту, не должен создавать дубль при восстановлении. Сбой между записью состояния и постановкой задания не должен терять фоновое действие: сохранять их согласованно.
8. Подтверждённая отмена — только после ответа Google/сверки отсутствия. Не освобождать слот по одному факту нажатия «Отменить»; повторная отмена возвращает текущее состояние, автор отмены сохраняется.
9. Ошибки Telegram не откатывают уже подтверждённое событие. Сохранить дедупликацию уведомлений и задач. При неизвестном результате отправки внешнему Telegram возможен повтор доставки; не обещать математическое «ровно один раз» для сети, но не создавать вторую бизнес-заявку или Google-встречу.
10. Выводы о сегодняшних гарантиях должны подтверждаться тестами. Новые сценарии гонок — обязательная проверка расширения, даже если похожий тест чата уже проходил ранее.

## 11. Данные, миграции и обратная совместимость

### 11.1. Возможные изменения схемы

Не требуется вторая база бронирования или перенос на новую СУБД. Предварительно могут потребоваться таблицы хешей сессий/обменов, реестр идемпотентных команд, ревизии редактируемых объектов и общий черновик. Конкретные имена/DDL фиксируются после D-04/D-07 и анализа миграции; само ТЗ их не создаёт. Локально в MA-2 подготовлена миграция v10; рабочая база не менялась.

Сохранить visitors, consents, access_requests, meeting_templates, availability_intervals, manual_blocks, bookings, meetings, jobs, notifications и audit_actions с их историей. Источник channel может быть добавлен как диагностическое поле, но не создаёт вторые статусы/таблицы бронирований. Не хранить исходные initData, OAuth или bearer в этих таблицах.

### 11.2. Требования к миграциям

- Следующие миграции после существующих 001–008 оформляются отдельными файлами; применённые SQL не переписываются.
- Проверить обновление с v8, пустую установку, повторный запуск, частичный сбой и последующее восстановление на тестовой базе со всеми активными состояниями и очередями.
- Проверить foreign_key_check, integrity_check, ограничения пересечений, количество и ключевые связи заявок/встреч до и после. Сохранить номера, event_id, дедупликационные ключи, сроки, роли и снимки.
- Для переноса черновиков описать mapping visitor_dialogs/drafts; нельзя автоматически подать старую форму, продлить hold или потерять ссылку на занятую заявку.
- Один управляющий процесс применяет миграции; startup API и polling не соревнуются за изменение схемы. Перед записью incompatible schema остановить изменяющие процессы по согласованному окну.
- Сначала проверить схему и совместимость, затем принимать трафик. Предыдущий код не должен запускаться против непроверенной новой схемы.

**Откат:** до релиза подготовить таблицу «версия bot/API/worker → поддерживаемая схема». При несовместимой миграции вариант простого переключения образа запрещён. Предпочесть совместимое расширение и согласованную версию всех процессов; при необходимости исправлять вперёд. Любой план восстановления данных должен учитывать заявки, созданные после релиза: нельзя молча восстановить старую базу и потерять новые встречи.

Автоматические резервные копии остаются вне обязательного scope по принятому решению. Разовая согласованная копия перед конкретной миграцией — отдельный вариант D-09, не внедрение фонового backup. Если копия согласована, получать согласованный снимок SQLite штатным способом, не копировать один файл активной WAL-базы. Без копии документировать пределы восстановления и не обещать возврат данных после разрушительной ошибки. .env не включать в копии кода или выгрузки базы.

### 12.2. Короткая ручная приёмка владельцем

1. Открыть тестового бота со второго аккаунта, затем Mini App: слоты закрыты, доступ можно запросить отдельно от согласия.
2. С аккаунта администратора разрешить запрос через чат. В Mini App посетителя обновить статус: календарь стал доступен.
3. Выбрать шаблон, длительность, платформу и время; проверить 10-минутное удержание и итог контактов/часового пояса; отправить один раз.
4. Открыть ту же заявку в административном Mini App, согласовать и вставить тестовую ссылку. До Google экран не показывает финальное подтверждение.
5. Проверить одно событие в календаре, приглашение на тестовом email, сообщение в чате посетителя и тот же статус в обоих интерфейсах.
6. Отменить встречу из чата посетителя при допустимом сроке; в Mini App дождаться подтверждённой отмены и проверить удаление события.
7. Изменить шаблон/закрыть время в Mini App администратора и проверить, что чат использует новые данные, сохранив старую карточку заявки.

Отсутствие письма в inbox само по себе не доказывает ошибку API: результат приглашения и настройки почты проверяются раздельно. Для приёмки фиксируется фактический результат, непроверенные пункты не отмечаются выполненными.

## 13. Развёртывание и сохранение работающего бота

### 13.1. Окружения

| Окружение | Код и данные | Назначение |
|---|---|---|
| Локальная разработка | dev; синтетические данные и временная SQLite | Реализация и автоматические проверки после отдельного поручения |
| Тестовый HTTPS-контур | Согласованный адрес, отдельный тестовый бот/токен, SQLite и Google-календарь | WebView, Telegram-auth, приглашения и сбои; без рабочей базы и без polling рабочим токеном |
| Рабочее | Только согласованная main; /opt/meeting-bot/data/bot.sqlite | Существующий @MyMeetPlanning_bot и добавленный Mini App после отдельного разрешения |

Тестовый контур может быть изолированным Compose-проектом на согласованном хосте. Его создание на рабочем VPS требует отдельного решения о ресурсах и адресе. Данные клиентов не копируются на тестовый хост как обычная fixture.

### 13.2. Предлагаемый способ размещения — D-03

Сохранить Docker Compose и существующие bot/worker. Добавить отдельный API-сервис с контролируемыми ресурсами; статику собирать вне рабочего runtime и отдавать nginx. Возможный адрес — https://meetcalendar.fin-partner.pro/app/, API — тот же origin /api/v1/. Это предложение, не уже настроенные URL.

Корень сайта, политика, сертификат и другие сервисы VPS сохраняются. API публикуется только через HTTPS reverse proxy, внутренний порт не открывается в интернет. .env, data и logs остаются вне образов на постоянном диске. Сборка интерфейса не получает реальные секреты; зависимости фиксируются после согласования инструментов.

Минимум один экземпляр polling и один согласованный worker. API не запускает polling и не получает Telegram updates параллельно с ботом. Настроить readiness без раскрытия конфигурации и без постоянных дорогих вызовов Google; liveness отделить от временных сбоев внешнего сервиса.

### 13.3. Последовательность первого релиза

1. Согласовать ТЗ, D-01–D-09 в нужном объёме и отдельное поручение на реализацию. Весь код и документация разрабатываются в dev.
2. Реализовать и проверить общие изменения на тестовом контуре. Подготовить конкретный diff, миграции, версии bot/API/worker, сценарий отключения и сведения о ресурсах.
3. Настроить dev CI для frontend/API после выбора инструментов; сохранить регрессию Python, проверку секретов и существующих auto-deploy ограничений. Не подключать dev к рабочему обновлению.
4. До отдельного разрешения не выполнять merge/push в main. Учитывать, что main запускает auto-deploy после CI: разрешение на merge для релиза должно включать понимание его серверного эффекта.
5. Первый инфраструктурный релиз провести управляемо: согласованно остановить/приостановить auto-deploy на время операции, применить контейнерную конфигурацию, nginx/статику и миграции в определённом порядке. Текущий scripts/auto_deploy.py не предназначен для самостоятельного применения изменений compose.yaml/Dockerfile и migrations; его защиту не обходить. После релиза зафиксировать новый baseline и проверить безопасное возобновление таймера.
6. Применять схему одним процессом в согласованном окне; при необходимости кратко приостановить изменяющие действия bot/API/worker. Установить совместимые версии всех процессов, проверить базу и сохранность секретов, не печатая их.
7. Включить API/статику сначала только для тестовых Telegram ID; администратор проходит smoke test. Allowlist должен проверяться сервером и не заменять обычный ручной допуск.
8. После успешной проверки и отдельного разрешения настроить кнопки/меню рабочего бота и открыть Mini App согласованной аудитории. Это не отменяет правовую зависимость перед дальнейшим использованием с клиентами.
9. Проверить real end-to-end, фоновые сроки, логи, нагрузку и сохранность данных. Перезагрузку всего VPS не включать автоматически: она требует отдельного разрешения и учёта других сервисов.

### 13.4. Отключение и восстановление

Предусмотреть серверный feature flag доступа к Mini App. При проблеме отключить новые HTTP-команды и вход, вернуть понятное сообщение со ссылкой на чат; bot и worker продолжают обслуживать уже созданные заявки. Отключение UI не должно отменять записи или терять незавершённые Google-операции.

Статику можно вернуть к совместимой версии. Откат Python-образов — только по матрице совместимости со схемой, особенно после повышения SCHEMA_VERSION. Если безопасного отката нет, оставить Mini App выключенным, сохранить работающие совместимые bot/worker и исправить вперёд. Предыдущая SQLite не заменяется молча.

Инструкция владельцу должна содержать: как открыть приложение, вернуться в чат, увидеть сбой/статус, сообщить request_id или номер заявки, кто включает/отключает релиз. Техническая инструкция исполнителю: пути/сервисы, флаги, миграции, health checks, обработка очереди, процедура релиза и восстановления без значений секретов.

## 15. План реализации и порядок согласования

Подробный рабочий план находится в [telegram_mini_app_plan.md](telegram_mini_app_plan.md): статусы, чекбоксы, результаты, проверки, ручная приёмка и журнал каждого этапа. Он относится к Mini App; незавершённые пункты MVP 6–7 остаются в прежнем плане бота.

На подготовительном этапе разрешена работа с документацией. Выбор пошагового сценария или согласие с ТЗ не являются автоматическим разрешением на весь код/развёртывание. После разрешения конкретного программного этапа исполнитель выполняет обычные обратимые действия и проверки самостоятельно, без запроса подтверждения каждого файла. Границы следующих этапов фиксируются в поручении; main/VPS остаются отдельной границей.

Ответы пользователя записываются в реестр один раз. Уже установленные правила не превращаются в повторные вопросы. Решения принимаются тогда, когда они влияют на следующий этап: внешний вид — до UI, модель черновика/права/сессии — до схемы и API, инфраструктура миграции — перед рабочим релизом.

При завершении реализации передаются исходники, контракт, миграции, тесты/отчёт, инструкция, матрица совместимости и реестр решений. Токены, действующие контакты и рабочая база в поставку не входят. Текущий локальный результат и оставшиеся внешние проверки отражены в рабочем плане и протоколах MA-1/MA-2.

### Уточнение реализации MA-3 — 11.10.2026

По поручению владельца работающий локальный интерфейс посетителя допускается до появления отдельного тестового бота/HTTPS. Он использует общий API и сервисы на отдельной вымышленной базе; вход по фиксированным тестовым персонам доступен только в специальном loopback-приложении local_preview.py, отсутствует в production factory и не заменяет проверку Telegram initData. MA-2 остаётся открыт по настоящему WebView-входу.

Контракт расширен: PATCH /api/v1/me/draft (revision, template_id, duration_minutes, video_service, selected_day — полный выбор до удержания) и DELETE /api/v1/me/draft (revision, confirmed=true — общий сброс с освобождением hold). Удержанный слот изменяется только через явное освобождение; CAS и идемпотентность обязательны. GET /api/v1/me/bookings принимает group=review|upcoming|history, фильтрация/порядок выполняются сервером до пагинации, курсор связан с группой. Актуальные DTO — docs/mini_app_openapi.json, генерируемые frontend-типы проверяются в dev CI.

Протокол localhost, результаты проверок и открытые ограничения — [mini_app_visitor_stage.md](mini_app_visitor_stage.md). Это дополнение не разрешает изменения main, VPS или реальных данных.
