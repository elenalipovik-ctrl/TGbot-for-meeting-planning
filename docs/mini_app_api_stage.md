# MA-2: API и Telegram-auth

Дата: 11.10.2026. Ветка: dev. Статус: локальная реализация готова; настоящий Telegram WebView ещё не проверен. MA-2 остаётся «В работе».

## Что реализовано

FastAPI создаётся явной фабрикой api.app.create_app. Импорт не читает .env, не создаёт базу и не выполняет миграции. Все команды используют BookingService / DraftStore / Commands; правила времени из rules.py сохранены. Без второй базы бронирований и копии календарных правил.

Контракт: [OpenAPI](mini_app_openapi.json), строгие входные модели api/models.py и выходные api/outputs.py. Фактические ответы проверяются по выходным DTO. Ошибки имеют безопасные code/message/field_errors/retryable, server_time/request_id. Публичная выдача OpenAPI и Swagger отключена. Списки: limit 20, максимум 100; подписанный cursor привязан к роли/пользователю и фильтру. Cursor содержит смещение: при одновременном изменении списка следует обновить первую страницу; гарантия неизменного снимка не заявлена.

Реализованы методы обеих ролей из ТЗ §8, включая отдельный GET /admin/manual-blocks и явное POST /holds/{booking_id}/use-saved-contacts. API возвращает Telegram ID строкой. Сервер сам определяет пользователя/роль/время/получателей уведомлений. GET /slots принимает from_time/to_time в ближайших 7 сутках; история — status/from_time/to_time. Все пути приведены в OpenAPI.

Согласованные D-07: исходные initData действуют 300 секунд, допускается будущее до 30 секунд; абсолютная сессия 1800 секунд; реестр команд 86400 секунд. Bearer — 32 случайных байта, только память страницы; в SQLite SHA-256. Сохраняется минимальный проверенный username из Telegram для снимка заявки при последующей подаче, без полного user JSON/имени/аватара. Это метаданные сессии, удаляемые по её TTL. Права перечитываются на каждом запросе и внутри транзакции изменения.

HMAC-проверка следует [официальному алгоритму Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app): исключается hash; signature, если прислана, участвует в HMAC. Дубли/неверное кодирование/неверные типы отклоняются. Отпечаток replay строится из проверенной канонической строки и подписи: перестановка query-пар не даёт нового входа. Потеря ответа обмена требует переоткрыть Mini App, а не повторно выдать bearer.

Стартовые ограничения: вход 10/мин/IP, чтение 60/мин/сессия, изменения 20/мин/Telegram ID, hold 6/мин/Telegram ID, явная Google-проверка 2/мин/администратор. Скользящее окно 60 секунд хранится в общей SQLite. Измерение нагрузки — MA-5. Запускатель слушает только loopback и не доверяет Forwarded/X-Forwarded-For. Пока auth IP — адрес непосредственного соединения: за HTTPS-прокси лимит общий для прокси. До внешнего теста отдельно проверить/настроить доверенный proxy без возможности подделать IP; поднимать лимит бесконтрольно нельзя.

## Повторы и внешние вызовы

Для всех изменяющих бизнес-команд нужен Idempotency-Key: 16–128 ASCII-символов из букв, цифр, точки, подчёркивания, дефиса, двоеточия. Область — actor + HTTP method + фактический путь. Ключ и нормализованное тело хранятся как HMAC, результат — только безопасные ссылки/ID, без копии контактов или response. Повтор перечитывает текущее разрешённое состояние. Другой запрос с прежним ключом → 409 IDEMPOTENCY_CONFLICT. Повторная выдача не возвращает удалённые контакты и не обходит блокировку.

unit_of_work связывает локальные сервисные транзакции savepoint-ами с одной командной транзакцией. Данные/очереди/результат операции коммитятся вместе; события об успешном изменении пишутся в журнал после внешнего COMMIT. FreeBusy подготавливается до write-транзакции; общие правила и ревизия повторно проверяются при записи.

Добавление видеоссылки сначала устойчиво сохраняет намерение и прежний Google event ID, затем вызывает общий confirm_with_google вне транзакции. Lease 120 секунд предотвращает одновременный внешний повтор; другая обработка возвращает 202. После рестарта/истечения lease тот же ключ сверяет прежнее событие и продолжает команду. GET /operations/{operation_id} доступен владельцу операции с повторной проверкой текущих прав. 202 означает принятие, не подтверждённую встречу. Отмена подтверждённой встречи ставит существующее задание; до подтверждения Google возвращается состояние attention/cancellation_pending.

Google GET возвращает последний проверенный status/checked_at/error_code/stale. POST check действительно вызывает FreeBusy; истёкший OAuth и отсутствие прав ставят безопасное Telegram-уведомление в общую очередь. Отсутствующий календарь сообщает unavailable, не имитирует успешную работу. Проверка устаревает через 300 секунд. Администратор не получает credentials, calendar/event ID или детали личной занятости.

## Подготовленный изолированный запуск

Сейчас отдельного тестового бота, календаря и согласованного HTTPS-адреса нет — это подтвердил владелец. @MyMeetPlanning_bot рабочий; его настройки не используются. Реальные .env/SQLite/VPS не читались и не изменялись. Команды ниже предназначены исполнителю после подготовки тестового контура; владельцу не требуется запускать терминал.

1. Владелец создаёт через свой Telegram-аккаунт в @BotFather отдельного бота командой /newbot. Имя, например, MyMeetPlanning Test; username должен быть уникальным и отличаться от рабочего. В чат достаточно передать username; токен сюда не присылать.
2. Исполнитель готовит согласованный HTTPS-адрес тестового контура на отдельном хосте/туннеле. Никаких изменений main, auto-deploy или VPS без отдельного разрешения. Конкретный сервис/домен ещё не выбран и не развёрнут. Адрес должен проксировать /auth-check и /api/v1/* к loopback API одного origin. Прокси не пишет тела, Authorization или токены, ограничивает JSON до 16 KiB и время ожидания; сертификат валиден. Auth IP за прокси проверяется отдельно.
3. На локальном компьютере создать .env-miniapp-test по [шаблону](mini_app_test.env.example). Владелец сохраняет тестовый токен только там. Не копировать рабочий .env целиком. Вписать отдельного бота, Telegram ID администратора, HTTPS origin и актуальную политику. Файл исключён .gitignore.
4. Для настоящих календарных команд отдельно создать тестовый Google-календарь и выдать нужный OAuth-доступ. Указать именно его ID, MINI_APP_CALENDAR_IS_TEST=true и тестовые credentials. Без этих значений проверка auth возможна, а бронирование безопасно получает 503 от отключённого календаря. primary запрещён. Изоляцию календаря проверяет исполнитель до реального создания события.
5. Установить локальные зависимости и запустить:

~~~powershell
.\.venv\Scripts\python.exe -m pip install -e '.[test,api]'
.\.venv\Scripts\python.exe -m meeting_bot.api --env-file .env-miniapp-test --port 8765
~~~

Запускатель проверяет через Telegram getMe, что токен соответствует указанному отдельному тестовому боту; рабочий @MyMeetPlanning_bot отвергается независимо от значения TEST_BOT_USERNAME. База и журнал строго в .secrets/miniapp-test/test.sqlite и api.log. Перенаправленные каталоги/символические ссылки и hardlink базы запрещены. Рабочие data/bot.sqlite и .env недоступны через выбор параметров запуска. Реального запуска пока не было: нужного тестового токена нет.

Сторонние access/debug журналы отключены; собственный JSON-журнал содержит только event/code/record_id/request_id/route-шаблон/method/status/duration_ms. Не включает URL-параметры, произвольный путь, IP, тела и тексты исключений. Отдельный API не запускает рабочий polling/worker. Для будущего сквозного теста нужны отдельно настроенные тестовые bot/worker с этой же базой и allowlist получателей — MA-5; текущая очередь проверена внедрённым тестовым транспортом без сообщений людям.

6. В BotFather только у тестового бота настроить меню Web App на https://TEST_HOST/auth-check. Страница минимальная, для MA-2: Telegram SDK → обмен initData → bootstrap → проверенная роль/допуск → выход. Это не согласованный продуктовый React UI, который относится к MA-3/MA-4. Вне Telegram поддельного входа нет.
