# MA-1: общий слой Mini App и чат-бота

Дата: 11.10.2026. Ветка: dev. Рабочая схема остаётся v8 до отдельного релиза; подготовленная локальная схема — v9.

## Решения и область этапа

Пользователь принял React + TypeScript + Vite для интерфейса и FastAPI для HTTP API. Зависимости ещё не устанавливались: на MA-1 нет HTTP-сервера и рабочего frontend.

D-04: по поручению пользователя самостоятельно выбран один общий черновик на посетителя. Возврат предлагает продолжение или явный сброс; меню сохраняет незавершённую форму. Это ограничение формы, а не количества поданных заявок.

D-05: пользователь выбрал прежний полный запрет для заблокированного посетителя. Дополнительного доступа к встречам/профилю через Mini App нет. Блокировка не отменяет поданные/подтверждённые встречи. Незавершённый черновик и hold при отзыве допуска сбрасываются.

D-07 (сессия, initData, replay, идемпотентность и HTTP-лимиты) остаётся решением MA-2. В v9 нет таблиц сессий или ключей команд; длительности бронирования/рассмотрения и хранения данных не менялись.

## Общие компоненты

| Компонент | Ответственность |
|---|---|
| validation.py | Общие проверки имени/текста, email, телефона, HTTPS-видеоссылки и домена провайдера; flow-классы используют их |
| errors.py | Ошибки правил, доступа, конфликта версии, слота и временного отказа SQLite; прежние импорты из service.py сохранены |
| drafts.py / DraftStore | Каноническая форма, версия, чтение/очистка по срокам, изменение контактов, сброс с освобождением hold |
| queries.py / Queries | Авторизованные списки/карточка заявки, шаблоны, посетители, интервалы, история, очередь, агрегаты статистики; чат использует общую историю/очередь/статистику |
| commands.py / Commands | Защищённые точки входа подачи из канонической формы, удержания, согласия, решения, видеоссылки и отмены; actor берётся только из проверенного транспорта |
| service.py, rules.py, calendar_flow.py | Единственные бизнес-правила и переходы; транзакционная проверка состояния и версии после внешнего запроса; существующая Google-интеграция |
| worker.py | Прежние задания, включая истечение и удаление канонической формы; отдельного планировщика для Mini App нет |

Queries возвращает внутренние модели/кортежи, а не окончательные HTTP DTO. Пагинация внутри слоя limit/offset ограничена 100; внешний cursor и единый формат ошибок оформляются в MA-2. Отдельные SQL-выборки для текстов чата остаются в flow-классах, новой логики бронирования в них не добавлено.

## Матрица границ доступа

| Действие | Проверка в общем слое |
|---|---|
| Запрос допуска и первоначальное согласие | Существующий сценарий request_access; consent разрешён pending/allowed, запрещён blocked/rejected |
| Черновик/контакты/история/собственная карточка/слоты/подача/отмена | Допуск allowed на каждом действии; владение по actor, чужая заявка не выдаётся |
| Очередь/статистика/пользователи/интервалы/все шаблоны | Точное совпадение с настроенным ID администратора |
| Решение/ссылка Google/админ-отмена/шаблоны/публикация | Общие административные команды или уже защищённые методы BookingService |
| Сверка/создание/удаление Google, обработка jobs | Внутренние доверенные операции; не HTTP endpoints |
| Bootstrap pending/rejected/blocked | Только статус допуска и безопасные пояснения; HTTP-реализация в MA-2 |

Нельзя публиковать все методы BookingService через HTTP автоматически. booking_window, calendar_booking, mark_calendar_*, reserve_google_event_id, низкоуровневый reserve_slot и DraftStore.save предназначены для внутренних операций. В HTTP запрещены actor_id/visitor_id из тела как доказательство личности, произвольные SQL-поля и callback-команды браузера. HTTP-адаптер выбирает явную команду и подставляет actor из проверенной сессии. policy_version для Commands — серверная конфигурация, username — доверенный контекст Telegram.

## Черновик и конкурентные изменения

Канонические контакты/цель и шаг хранятся в visitor_dialogs. drafts сохраняет только метаданные удержания; его старые контактные поля обнуляются миграцией. На одного посетителя допускается один held в bookings: частичный уникальный индекс работает между процессами.

Черновик имеет revision. Счётчик draft_generations переживает удаление строки формы, поэтому прежняя версия не становится актуальной после сброса. INSERT/UPDATE/DELETE канонической формы повышают счётчик триггерами. BEGIN IMMEDIATE сериализует сравнение версии и запись.

- Каноническая сессия шага: прежние 30 минут. Hold: прежние 600 секунд. Это разные сроки.
- Автосохранение контактов не изменяет hold_expires_at и не продлевает его.
- В точности при now >= hold_expires_at удержание истекает; worker и чтение формы удаляют соответствующий черновик.
- Изменение контактов сбрасывает признак использования сохранённых контактов; браузер не устанавливает этот признак произвольно.
- Сброс явно освобождает hold. Новая запись при существующей форме предлагает продолжить/сбросить.
- Telegram-кнопки формы и профиля содержат версию r:revision:action; старые кнопки без версии адаптер отклоняет. Публичные HTTP-команды требуют целую неотрицательную revision; None не отключает проверку.
- Для bookings, visitors, meeting_templates, availability_intervals добавлена revision. Решение/отмена/редактирование профиля/шаблона/закрытие интервала поддерживают проверку версии в транзакции. Длительные формы шаблона/видеоссылки администратора сохраняют исходную версию.
- Прежние внутренние вызовы совместимы без обязательного аргумента revision; HTTP не должен использовать этот режим. Существующие проверки статусов/дедлайнов сохраняются независимо от версии. Общая HTTP-идемпотентность остаётся MA-2.

Удаление контактов очищает профиль и контактные поля всех серверных форм и меняет версию даже при отсутствии формы. Само по себе оно не отменяет hold или поданную заявку, в том числе в чате; связанная форма возвращается к вводу имени. Отзыв согласия очищает контактную форму и блокирует подачу до нового согласия; встреча остаётся. Старые версии формы и согласия отклоняются. Исправление профиля также инвалидирует старую форму. Снимки в уже поданных заявках сохраняются по прежним правилам.

Транзакции не охватывают Google-вызовы. Общая подача читает форму/права, вызывает FreeBusy и снова проверяет допуск, версию, согласие, сроки, шаблон, интервал и занятость внутри короткой записи. Тест FreeBusy получает вторую SQLite-блокировку записи во время внешнего вызова — доказательство отсутствия открытой write-транзакции. WAL, foreign_keys, synchronous=FULL и busy_timeout=3000 сохраняются; DraftStore переводит отказ SQLite в безопасное сообщение без SQL/контактов.

## Миграция v8 → v9 и совместимость

009_shared_drafts.sql выполняется штатным initialize_database в одной транзакции. При ошибке v9 откатывается вместе с user_version.

Mapping старой базы:

1. Если у посетителя несколько holds, сохранить held, на который указывает текущий чат-диалог; иначе самый новый по created_at/id. Остальные перевести в expired, задания их истечения завершить.
2. Создать отсутствующую каноническую форму для сохранённого hold. Если старая форма указывает на другой объект/не имеет связи, перепривязать её и убрать чужие контактные значения.
3. Дополнять отсутствующие контакты только метаданными того же hold. Существующие канонические значения приоритетны.
4. Удалить лишние метаданные и обнулить их контактные копии. Добавить уникальные индексы, версии и триггеры.
5. Поданные заявки, контакты-снимки, встречи и Google ID не переписывать. Миграция не вызывает Google/Telegram. Просроченные retained holds затем обрабатываются обычным worker/чтением.

| Компонент | Допустимая схема |
|---|---|
| Нынешняя main, код до MA-1 | v8; при запуске initialize_database на v9 отказывает как на более новой схеме |
| dev после MA-1 | v9; initialize_database обновляет копию v8 до v9 |
| Будущий API | v9 или согласованная последующая версия совместно с bot/worker |

Нельзя обновлять живую базу рядом с продолжающим работать старым bot/worker: проверка версии выполняется при запуске и не останавливает уже работающий старый процесс. Потребуется согласованная остановка всех писателей, snapshot и совместимый релиз bot/API/worker. Одна копия SQLite-файла при активном WAL не является корректным backup.

## Репетиция и восстановление

Все проверки MA-1 используют pytest tmp_path. Рабочие .env, /opt/meeting-bot/data/bot.sqlite и VPS не читались и не менялись.

Локальная повторяемая проверка из корня проекта:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 -m pytest tests/test_shared_migration.py tests/test_shared_drafts.py tests/test_shared_commands.py
~~~

test_shared_migration создаёт схему v8 и синтетические дубли, переносит в v9, повторяет инициализацию, проверяет integrity_check/foreign_key_check, снимки и уникальность. Второй тест создаёт snapshot через sqlite3.Connection.backup, имитирует ошибку после DDL, проверяет откат на v8, затем обновляет и восстанавливает snapshot v8; проверена сохранность структуры.

Для будущей репетиции на разрешённой копии: подготовить копию через SQLite backup API; записать версию схемы и сборки; выполнить штатную миграцию копии; проверить integrity_check/foreign_key_check, число/статусы заявок, retained holds, jobs и снимки; запустить совместимые компоненты и smoke test. Секреты и настоящие контакты не включать в отчёт.

При неуспешной миграции — сохранить диагностику без PII и убедиться в исходной версии; при необходимости восстановить snapshot после остановки всех писателей. После начала новых записей v9 восстановление старого snapshot теряет новые данные: сначала согласовать их сохранение/восстановление. SQL downgrade не подготовлен и не обещается. Отключение UI/API не требует возврата базы на v8: совместимый bot/worker v9 может продолжать работу. На рабочем контуре эти действия относятся только к MA-6 и требуют отдельного согласования.
